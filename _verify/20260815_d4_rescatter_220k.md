## The gradient, and why it is not one ramp

The height band was a HARD window: inside `[120, 640] m` every elevation was
equally likely, which plants uniform density right to the top edge and then
stops dead. WORLD_VISION's complaint about the old forest was **UNIFORMITY
as much as sparseness**.

New shared prior `placement_priors.closure_ramp`, and it deliberately
**SCALES** where `centred_bias` **REDISTRIBUTES**. Flow says WHERE trees
prefer to stand; closure says HOW MANY there are. A subalpine stand
genuinely thins toward treeline — fewer trees, not the same trees moved
uphill — so anything preserving the mean would describe a forest that does
not exist.

**The falloff differs by TIER, which is the compositional half of the
ruling.** One shared ramp would thin all four species together and produce a
small copy of the same forest:

    Conifer        1.00 -> 0.15    29.3 m canopy; a mature crown goes first
    ConiferPine    1.00 -> 0.20    canopy, marginally hardier
    SpruceSub      1.00 -> 0.30    16.7 m sub-canopy
    SpruceSapling  1.00 -> 0.55    4.5 m regeneration — this IS the krummholz

So the top of the band ends **sapling-dominated rather than empty**, and the
acceptance rates above show it working: the sapling tier accepts 30.0% where
the canopy accepts 22.4%.

**Density was RE-DERIVED against the ramp, not carried over.** Measured at
the unchanged 68/ha, closure alone takes the plan to 111,079; 135/ha then
gives 219,659.

## A gate that refused correctly, and would have saved the wrong world

`save_level.py` defaults to `recipes/alpine.json`. Run without `--recipe`,
its LEVEL GATE refused (exit 7): *"recipe targets '/Game/Alpine' but the
editor has '/Game/Alpine8K' open"*. That is not a formality — the tool
carries a package ALLOW-LIST derived from the recipe, so it would have
saved with a list scoped to a different world. Re-run with
`--recipe recipes/alpine_8k.json`.
